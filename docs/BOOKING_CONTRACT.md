# Booking implementation contract

This documents the local booking application's interfaces. The booking extension is on `dev`; the existing live static website and main deployment remain separate.

## Runtime

- Existing static public Caddy website remains the `web` service on internal port 8080. Proxy `/api/public/*` to `booking:8081`.
- A single Go service under `booking/` listens on 8081 (public API only) and 8082 (admin UI + admin API + OAuth callback). Embed `booking/web/` in the Go binary. SQLite and the encryption key live under `/data` on a persistent local volume. No external database or queue.
- Root Dockerfile stays the static site image. `booking/Dockerfile` builds the Go backend. Local Compose builds and starts both. Preserve current production files: provide a separate future booking production template, never change the active deployment workflow into a release of this backend.
- Environment: `PUBLIC_ORIGIN`, `ADMIN_ORIGIN` exact browser origins (including dynamically selected ports); `DATA_DIR=/data`; `BOOTSTRAP_TOKEN` random per-install admin bootstrap secret, generated in ignored `.local/` and preserved on update. `GOOGLE_CLIENT_ID` optional override; default from `booking/config/google-client.json` (public desktop client ID only). `GOOGLE_OAUTH_MODE=desktop` default, web optional with secret supplied only via private environment. Web mode requires configured HTTPS origin/client credentials.
- Configured local installations open `ADMIN_ORIGIN/` for Google sign-in. Only an unconfigured installation opens `ADMIN_ORIGIN/#setup=<BOOTSTRAP_TOKEN>` without printing the token. The UI clears that fragment and exchanges it for a limited setup session; Google verifies the identity before operator access is granted. Google login recognizes an approved operator or invited owner; there is no open self-registration. A configured operator or existing owner disables bootstrap access. Private operator identity provisioning is separate from personal Google tokens. Origin/CSRF checks for writes, install-specific cookie name, allowed Host validation, rate limits. Google tokens encrypted on disk. No token/secret/customer-data logs.
- Native Google OAuth uses PKCE S256, short-lived single-use state tied to the initiating browser, callback `/oauth/callback`, offline refresh, and scopes `openid`, `email`, `calendar.app.created` and `calendar.freebusy`. No Gmail scope. Create a dedicated booking calendar visible in the owner's Google Calendar; check busy times in both primary and booking calendars. Store the verified email, stable subject and dedicated calendar ID in the encrypted owner record, preserving the calendar ID across reconnects. Event writes are retried using stable IDs. No confirmation is claimed until sync succeeds. Handle cancellation and disconnect. No fake OAuth UI.

## Calendar edits

The app reads changes from its dedicated booking calendar using Google’s incremental sync token, kept encrypted in the local data volume. A background check runs at most once per minute, with fresh reads before publishing slots, accepting new bookings and returning the owner’s booking list. Timed event moves/resizes update start, end and occupied time, retaining the booking’s original buffer and follow-up status. Google deletions cancel the matching request. Refresh failures keep saved records visible with a warning and close public availability.

All-day changes use the Calendar timezone and exclusive end date. Turning a single booking into a recurring series is unsupported and requires restoring a single event; a sync warning appears until resolved. Moving an event to another calendar removes it from this installation. Personal calendar event details are never imported.

## HTTP interface (JSON)

- `GET /api/admin/session` → `{authenticated, csrfToken?, setupRequired?, google:{configured,connected,email?,error?,mode,requiresClientConfiguration?}, publicOrigin}`. Anonymous status may reveal only configuration booleans, never connected email. Frontend attaches `X-CSRF-Token` to authenticated writes.
- `POST /api/admin/bootstrap` `{token}` → same session object with a limited setup role, only on an unconfigured installation. The token is a local setup credential, never committed or displayed by the UI. CSRF-exempt only with strict Origin + token checks. Remove fragment before API call.
- `POST /api/admin/logout` → 204.
- `POST /api/admin/google/configure` `{clientId,clientSecret}` → 204. Authenticated, CSRF-protected, desktop mode only. The ID must match the configured client. Store private configuration encrypted in the persistent volume and never return the secret. The operator-controlled UI import/replace path remains available for application configuration recovery; normal initial setup uses the launcher's private GitHub retrieval. Google's real desktop endpoint rejected client-ID-only PKCE for this registered client. Private client secrets never belong in this public repository or its images.
- `POST /api/admin/signin` → `{url}` starts identity-only Google sign-in (`openid email`). `POST /api/admin/google/connect` → `{url}` requires an authenticated actor allowed to connect the business owner's Calendar and requests Calendar consent separately. `GET /oauth/callback` handles Google and returns to admin with safe outcome indicator. `POST /api/admin/google/disconnect` → 204.
- `GET /api/admin/settings` and `PUT /api/admin/settings`: `{businessName,timeZone,slotMinutes,estimateMinutes,bufferMinutes,externalBufferMinutes,minNoticeHours,horizonDays,weekly:[{weekday,start,end}],exceptions:[{date,closed,start?,end?}],blockedWeekly:[{weekday,allDay,start?,end?}],blockedDates:[{date,allDay,start?,end?}]}`. Weekday 0=Sunday. HH:mm local wall time, YYYY-MM-DD dates; IANA timezone default America/New_York. Defaults weekdays 09:00–17:00, 60-minute service appointments, 15-minute estimate/callback appointments, 15-minute business gap, 30-minute external Calendar buffer, 24-hour notice, 30-day horizon, and no time-off rules. Date exceptions replace usual working hours; weekly and date-specific time off subtract from those hours. Google busy times and existing reservations always take precedence. Older saved settings without the new block arrays behave as empty arrays.
- `GET /api/admin/bookings` → `{bookings:[{id,kind,start,end,serviceId,name,email,phone,address,notes,status,calendarStatus,createdAt,adminNotes}]}`. Optional status and kind filters; kind is service or estimate. `PATCH /api/admin/bookings/{id}` `{status?,adminNotes?}`; statuses needs_followup/contacted/confirmed/cancelled. Calendar synchronization is separate (`pending/synced/failed`). The list includes calendarSyncError when fresh Google changes could not be read. Allow retry through `POST /api/admin/bookings/{id}/retry`.
- `GET /api/public/config` → `{businessName,timeZone,slotMinutes,estimateMinutes,bufferMinutes,externalBufferMinutes,minNoticeHours,horizonDays,services:[{id,name}],bookingEnabled}`; services lawn-care/Lawn care, landscaping/Landscaping, snow-ice/Snow & ice. Customers request actual service visits at their property. New appointments reserve the owner’s configurable default duration; existing saved durations remain unchanged when that default changes. Name, email, phone and address are required; notes are optional. Estimate/callback requests use kind=estimate and reserve the independently configurable estimateMinutes duration. Missing kind means service for compatibility. Both kinds share availability and cannot overlap.
- `GET /api/public/slots?date=YYYY-MM-DD&kind=service` → `{date,timeZone,slots:[{start,end}]}` (RFC3339 UTC instants). Subtract local reservations, time off and buffered external Calendar events before generating appointment starts in each remaining free interval; fail closed on unavailable Calendar rather than publishing unsafe availability.
- `POST /api/public/bookings` `{kind?,serviceId,start,name,email,phone,address,notes,idempotencyKey}` → `{id,status,calendarStatus,start,end,message}`. Validate all fields/limits, enforce slot validity and transactionally prevent overlaps; never trust supplied durations. Handle repeated submissions idempotently.
- Both listeners have `/healthz`; public listener must not expose admin routes/assets/data. Errors `{error:"clear safe message",code?:"stable_code"}` with appropriate status. All API responses no-store.

## Frontend

- Preserve site theme/artwork. New public page `dist/book.html`, `dist/booking.css`, `dist/booking.js`, with prominent booking links in the main navigation, hero, contact section and mobile action bar. Do not replace verified phone contact.
- Admin files `booking/web/index.html`, `admin.css`, `admin.js`. Google connection, weekly availability/date exceptions, separate appointment and estimate/callback views with follow-up status and customer details, notes/cancel/retry, logout. Loading, error, disconnected, empty and success states; mobile usable, accessible controls; user data rendered as text.
- No customer accounts, payments, routing or property duration engine in this version.

## Launchers

- `./website.ps1 start` and `./website start` require Docker and Git. Authorized private Git access retrieves configuration on the first start. Choose usable ports automatically, print public/admin URLs and open the appropriate admin sign-in or initial setup page unless NoOpen. Existing start/update/stop/status/check commands remain.
- Persist install ID, bootstrap secret and port choices in ignored `.local/`; updates must not overwrite these or delete volumes. Handle two clones, occupied preferred ports, restart, update, and source-mounted dev. `stop` never deletes data. Document backup/restore without exposing credentials.
- On start/dev/update, check both `booking google-config status` and `booking operator-config status` in the healthy booking container: status 0 means present, 3 means absent, and 1 is a safe diagnostic failure. For missing configuration, use authenticated host Git to retrieve the corresponding `dev:google-client.json` or `dev:operator-access.json` from `Derek-Sykes/xsolutions-booking-private`, then stream it to its respective import command. Bound and validate each input and encrypt it locally without overwriting existing configuration. Never send GitHub credentials to the container. Remove the restricted temporary fetch on success/failure; do not open the browser until configuration succeeds. Build/check never require access to private GitHub.
- Checks build both images and run meaningful backend/integration tests. Do not require Google credentials in CI. Keep main-only existing static release unchanged; manual dev deployment is isolated from the existing main release (see DEV_DEPLOYMENT.md).

## Access roles and invitations

`GET /api/admin/session` also returns authenticated `role`, `actorEmail`, `canManageAccess` and `canConnectCalendar`. Identity-only sign-in leaves the saved Calendar grant unchanged. Google callback state records its purpose and initiating actor/session or invitation, alongside the PKCE verifier and browser binding.

Only the operator can call `GET/POST /api/admin/invitations` and `DELETE /api/admin/invitations/{id}`. Invitations are bound to the supplied verified Google email, normally expire in 24 hours, and are consumed atomically. `POST /api/admin/invitations/accept` takes `{token}` and starts invitation OAuth; it grants no session before Google's verified identity and the current invitation state pass validation. Full links appear only in creation responses. Subsequent list responses omit the token. Revoked, expired, used and superseded invitations cannot grant access. Different recipients' invitations stay independent; a replacement revokes only the same email's earlier unused link. Acceptance adds a workspace member without assigning or replacing the calendar account.

`GET /api/admin/members` returns `{members:[{id,email,role,calendarOwner,canRemove}]}` to the operator. `DELETE /api/admin/members/{id}` removes an invited owner's access; it requires operator authentication, same-origin and CSRF checks. Operator and assigned-calendar identities are protected. Removed accounts cannot use existing sessions, and a later invitation cannot revive an old revoked session. All active owners use the same booking records and settings. When no calendar has been assigned, an operator or active owner may explicitly connect their own Google account; the first successful authorized connection assigns that identity atomically. Subsequent membership changes do not replace the connection.

`operator-access.json` is an identity allowlist `{schema:1,email,googleSub?}`. `booking operator-config status/import/export` supports private host provisioning; imports use stdin, reject credential/unknown fields and refuse replacing a different saved operator. Personal tokens and invitations are not private Git configuration. The future hosted template accepts `OPERATOR_GOOGLE_SUB` and `OPERATOR_GOOGLE_EMAIL` privately; current main's static deployment is unchanged. See [admin operations](ADMIN_ACCESS.md).
